    - Ollama down             -> see step 0.3 below.
    - A tuned setting unset   -> see step 0.3 below.

------------------------------------------------------------------------------
0.3  If Ollama is DOWN, or a tuned setting is unset
------------------------------------------------------------------------------
Run this in a SEPARATE PowerShell terminal and leave it open for the demo:

>  taskkill /F /IM "ollama app.exe" 2>$null; taskkill /F /IM ollama.exe 2>$null
>  $env:OLLAMA_LOAD_TIMEOUT   = "20m"
>  $env:OLLAMA_KEEP_ALIVE     = "30m"
>  $env:OLLAMA_CONTEXT_LENGTH = "8192"
>  $env:OLLAMA_KV_CACHE_TYPE  = "q8_0"
>  $env:OLLAMA_FLASH_ATTENTION = "1"
>  & "$env:LOCALAPPDATA\Programs\Ollama\ollama.exe" serve

Then re-run:  python -m scripts.demo check

(Launching the "Ollama" app from the Start menu also works - it reads the
same persisted settings - but this way you see its log.)

------------------------------------------------------------------------------

------------------------------------------------------------------------------

  Expect: "162 passed". Run this if anyone asks about test coverage.

0.5  Refresh the public-site data from the current approved papers

==============================================================================
 PART 1  -  THE 60-SECOND STORY   (say this)
==============================================================================

"DIPT is an automated reading line for Software Engineering research papers,
 built for Professor Gorschek's group. It runs entirely on this one
 workstation with local models  -  no cloud, no cost.

 A paper goes in as just a title and an abstract. Six stages act on it in
 turn  -  fetch, parse, categorise, summarise, score, and a QA check  -  and
 it comes out fully read: sorted into subject categories, summarised in a
 fixed four-part structure, and given an industrial-relevance score from 1
 to 10 with a written justification, as if a CTO had triaged it.

 Every paper carries a status, so the line can stop and resume anywhere.
 There is an operator dashboard to drive and inspect it, an automated
 schedule, and a public website that publishes only the papers that pass QA."

Then move to the dashboard.

==============================================================================
 PART 4  -  QA HAS TWO MODES   (Professor Gorschek's requirement)
==============================================================================

The QA agent does not just flag problems. When it finds one it FIRST tries
to fix it automatically by regenerating the weaker output, and only
escalates to a human if that fails. Both paths are shown here on real
papers. The helper deliberately breaks a paper's stored summary so QA has
something to catch.

------------------------------------------------------------------------------
4.1  AUTO-FIX PATH    (about 4-6 minutes)
------------------------------------------------------------------------------
>  python -m scripts.qa_demo --autofix 946

  Watch the log: QA fails the paper for a missing summary, regenerates the
  summary, re-checks, and approves. Outcome: auto_fixed.
  Paper 946 is left cleanly approved  -  no cleanup needed.

------------------------------------------------------------------------------
4.2  ESCALATE PATH    (under a minute)
------------------------------------------------------------------------------
>  python -m scripts.qa_demo --escalate 929

  Regeneration is forced to fail, so QA gives up and writes a row to the QA
  queue for a person. Outcome: flagged.

------------------------------------------------------------------------------
4.3  SHOW IT IN THE DASHBOARD
------------------------------------------------------------------------------
Switch to the QA QUEUE view. Paper 929 is now there with the flag type,
description, and its stored summary and score. Click "Mark resolved" to
clear it  -  "and that is how a human closes the loop."

Paper 929's summary was deliberately corrupted. Restore it after the demo
with Part 7.
